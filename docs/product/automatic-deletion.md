# Approved automatic deletion

New tasks created in the app select this policy by default for two-way and mirror modes; Copy and Move keep it off and explain why. Existing stored preferences, including legacy tasks without a policy, are unchanged. Import and duplication keep the policy off. Monitoring, schedules and login triggers remain separate.

Selection and execution authorization are separate. The checkbox is usable before the first manual baseline, and the task can be saved with the policy selected. Saving a new selected policy, enabling it or changing its limits/triggers still requires a separate confirmation naming roots, limits and the manual-baseline prerequisite. The editor explicitly labels an unapproved selection as pending and explains the steps: save, full manual Preview, inspect and successfully Apply. It also explains off, approved and unsupported states beside the control.

The executor still independently requires a successful full manual Preview/Apply without unresolved conflicts. Schema 3 stores that manual run ID, root identities, mode and scope in `baseline_reviews`, transactionally with the successful terminal run. Automatic runs cannot create this approval. Old run history alone does not grant it. A scope change may be saved with the selected policy, but makes the previous approval inapplicable until another successful full manual reconciliation. Pending selection persists across restart and does not authorize deletion. No database migration or rewrite of existing preferences is required. Native default deserialization stays off for legacy/missing policy data; the new-task UI factory explicitly selects the supported-mode default.


Each queued plan counts proposed removals, including directories and descendants. Every surviving object must still match a non-null common baseline digest. Both limits must pass: maximum entry count (default 20) and maximum percentage of indexed, non-tombstoned common-baseline entries (default 10%). The denominator includes only baseline paths still represented in the scoped per-side index. It is an index-derived population, not a fresh whole-tree scan. Exact equality passes; integer multiplication avoids rounding. Limits apply per run, not across a rolling time window. Repeated small deletions can therefore exceed a limit cumulatively; the editor states this explicitly.

Mirror destination extras without baseline evidence remain manual. Move always remains manual. Missing roots, changed identities, partial enumeration, stale inputs and changed survivors retain existing failure/conflict protections. Deletion rechecks the opposite side is absent before protection and again immediately before file disposition; reappearance during a protected copy stops the run with both files intact. These checks cannot make two independent roots atomically consistent against a writer racing after the final check; the survivor recovery copy remains available. An empty result after successful enumeration is not automatically trusted for a large deletion: the percentage and entry limits still apply. User-selected 100% permits the whole indexed population only within the entry limit; the explicit confirmation shows this value.

Automatic authorization uses the existing verified protected-removal executor. It does not bypass preflight, immediate source/destination checks, recovery copying or atomic Windows deletion safeguards. Conflicts stay preserved while independent permitted operations run. A blocked destructive plan waits for exact-plan manual review, including any other operations in that plan.

Runs store a structured decision: reason, removal count, indexed baseline count, configured limits and approving manual run ID. Run details display that decision in English/German; basic logs retain these IDs/counts without paths. Approval records are removed with task configuration; protected versions retain existing recovery behavior.

Verification: actual native both-root delete events, protected versions, edit/delete conflict preservation, unrelated copies, exact percentage boundary, whole-tree loss, entry limit, directory descendant counting, unavailable root, restart, scope changes, import disabled and automatic-vs-manual approval separation. The UI unit test proves policy enabling does not save before its separate confirmation. Installed source 2575c0f additionally passed actual opt-in confirmation, hidden-window native deletion after one-second debounce with protected bytes, and a blocked 2/9 percentage-limit run displayed through real History. The blocked plan stayed unapplied; all fixture automation was disabled afterward. See qa-report.md and the auto-delete evidence files.


Current regression coverage includes saving a selected policy without approval, automatic-baseline deletion rejection before and after restart, unlocking through a successful manual reconciliation, scope-change rejection at execution, and mode restrictions. Frontend tests cover the new-task default, editable pending selection for existing tasks, explicit pending/off messages, and the separate save confirmation for both new and existing tasks.
