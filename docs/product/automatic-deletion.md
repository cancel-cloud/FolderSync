# Approved automatic deletion

New tasks created in the app select this policy by default for two-way and mirror modes; Copy and Move keep it off and explain why. Existing stored preferences, including legacy tasks without a policy, are unchanged. Import and duplication keep the policy off. Monitoring, schedules and login triggers remain separate.

Selection and execution authorization are separate. The checkbox is usable before the first manual baseline, and the task can be saved with the policy selected. Saving a new selected policy, enabling it or changing its triggers still requires a separate confirmation naming roots, absence of quantity limits and the manual-baseline prerequisite. The editor explicitly labels an unapproved selection as pending and explains the steps: save, full manual Preview, inspect and successfully Apply. It also explains off, approved and unsupported states beside the control.

The executor still independently requires a successful full manual Preview/Apply without unresolved conflicts. Schema 3 stores that manual run ID, root identities, mode and scope in `baseline_reviews`, transactionally with the successful terminal run. Automatic runs cannot create this approval. Old run history alone does not grant it. A scope change may be saved with the selected policy, but makes the previous approval inapplicable until another successful full manual reconciliation. Pending selection persists across restart and does not authorize deletion. No database migration or rewrite of existing preferences is required. Native default deserialization stays off for legacy/missing policy data; the new-task UI factory explicitly selects the supported-mode default.


Each queued plan counts proposed removals, including directories and descendants, for reporting only. There are no entry-count or percentage limits. Every surviving object must still match a non-null common baseline digest. All proven removals may therefore execute in one automatic run, including 100% of the known files when the original root remains reachable and correctly identified. External moves are propagated as their verified new paths and proven old-path removals; ambiguous renames remain conflicts.

Legacy `max_entries`/`max_percent` configuration values are ignored when loading and are omitted when saving/exporting. No database migration is needed. Historical EntryLimit/PercentLimit reason variants remain readable for old run history, labeled as former restrictions; new runs never generate those decisions. Create a new preview for such a historical blocked plan.

Mirror destination extras without baseline evidence remain manual. Move always remains manual. Missing roots, changed identities, partial enumeration, stale inputs and changed survivors retain existing failure/conflict protections. Deletion rechecks the opposite side is absent before protection and again immediately before file disposition; reappearance during a protected copy stops the run with both files intact. These checks cannot make two independent roots atomically consistent against a writer racing after the final check; the survivor recovery copy remains available. Successful complete enumeration of an empty, reachable original root can authorize all proven removals after the manual baseline prerequisite. This is intentional; missing, changed or partially enumerated roots still fail before deletion.

Automatic authorization uses the existing verified protected-removal executor. It does not bypass preflight, immediate source/destination checks, recovery copying or atomic Windows deletion safeguards. Conflicts stay preserved while independent permitted operations run. A blocked destructive plan waits for exact-plan manual review, including any other operations in that plan.

Runs store a structured decision: reason, removal count, indexed baseline count and approving manual run ID. Run details display that decision in English/German; basic logs retain these IDs/counts without paths. Approval records are removed with task configuration; protected versions retain existing recovery behavior.

Verification: actual native both-root delete events, protected versions, edit/delete conflict preservation, unrelated copies, unbounded bulk deletion, fully emptied reachable roots, bulk external moves, nested directory removal, unavailable root, restart, scope changes, import disabled and automatic-vs-manual approval separation. The UI unit test proves policy enabling does not save before its separate confirmation. Historical installed source 2575c0f (before quantity-limit removal) additionally passed actual opt-in confirmation, hidden-window native deletion after one-second debounce with protected bytes, and a blocked 2/9 percentage-limit run displayed through real History. The blocked plan stayed unapplied; all fixture automation was disabled afterward. See qa-report.md and the auto-delete evidence files.


Current regression coverage includes saving a selected policy without approval, automatic-baseline deletion rejection before and after restart, unlocking through a successful manual reconciliation, scope-change rejection at execution, and mode restrictions. Frontend tests cover the new-task default, editable pending selection for existing tasks, explicit pending/off messages, and the separate save confirmation for both new and existing tasks.


The global success, cancellation and error notices are rendered inside the fixed-height synchronization status dock. They no longer insert blocks above page content or use a separate settings overlay. Long feedback scrolls inside the dock. Browser layout checks at 800/1100/1920 pixels verify unchanged page geometry and scroll offset for completion, cancellation, long error, progress-with-error and idle states.
